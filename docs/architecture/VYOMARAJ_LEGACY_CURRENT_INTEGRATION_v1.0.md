# VYOMARAJ LEGACY → CURRENT ARCHITECTURE INTEGRATION v1.0

## Purpose
The current 2026 architecture is an additive integration of the older Vyomaraj/ShriYantra architecture. Nothing from the locked legacy control model is to be silently replaced by MCP, A2A, production agents, collaboration, media or monetization.

## Canonical inheritance

OWNER ROOT
→ SHRIYANTRA PRIVATE FOUNDATION
→ VYOMARAJ/BHARATH ↔ JARVIS/LAXMAN PEER CORES
→ LLM ROUTER + HARNESS
→ ARENA / PROVIDER-NEUTRAL EXECUTION FABRIC
→ AGENT + SUB-AGENT REGISTRY
→ DOMAIN / KNOWLEDGE / MEDIA / SOCIAL / EARNING
→ SECURITY + AUDIT + OBSERVABILITY
→ APPLICATION DR + MUTUAL RECOVERY

The newer layers are inserted into this chain, not placed above owner authority or outside ShriYantra governance.

## Legacy components that remain architectural requirements

### ShriYantra
Remains the private common foundation for identity, authorization, policy, security, RAG, CAG, MAG, memory, knowledge, evaluation, tools, events, tasks, audit and resilience.

### Peer cores
Vyomaraj/Bharath and Jarvis/Laxman remain equal peer cores with full authorized capability. Both inherit the same capability fabric and can observe, verify, recover and resynchronize the other.

### LLM + Harness
The model router selects among OpenAI, Claude, Gemini, Arena, local/open-source and specialist models. Harness remains the execution control boundary for prompts, tools, policies, validation and recovery.

### Arena
Arena remains a delegated build/execution environment where configured and authorized. Arena is not the root authority, system identity, memory owner or DR authority. Its results are untrusted until Harness verification.

### Hermes / resilience guard concept
The earlier Hermes integrity/continuity concept is preserved as a resilience responsibility: health monitoring, integrity checks, conflict detection, recovery coordination and failover/failback. It must not become a third root. Where an existing Hermes runtime is absent, the responsibility is implemented through the resilience/SRE/DR layer.

### Saptarishi / knowledge inheritance
Saptarishi-inspired knowledge inheritance remains a conceptual knowledge/governance layer feeding universal knowledge, wisdom, research, teaching and civilizational context. It is not a technical root and does not bypass evidence, policy or owner authority.

### Panch-Brothers
Matiman, Shrutiman, Ketuman, Gatiman and Dhritiman remain the universal capability fabric inherited by authorized agents and sub-agents.

### Kuber
Kuber remains Financial Controller for BOTH peer cores and the ecosystem. Every cost, revenue, invoice, receivable, payment, variance and settlement can be reconciled through Kuber. Kuber cannot become technical root.

### Content and taxonomy
The full domain registry, historical identities, aligned topics, products and provenance remain canonical. New Collaboration, media, MCP/A2A and creative agents inherit the same registry and content ownership rules.

### Universal knowledge
Education remains the civilization/universal-knowledge spine:
World → India → State/Region → District/City/Town/Village → Community/Local heritage.
Knowledge evolves:
Origin → Ancient → Classical → Medieval → Modern → Contemporary → Current → Trends → Future.
External knowledge remains data requiring retrieval, comparison, provenance, verification and rights checks.

### Dharmic daily startup
The existing configurable startup remains:
system health → owner authority → Shri Ram → Hanuman → Ganesha → peer sync → daily briefing.
It is cultural/spiritual and never grants technical authorization or blocks emergency recovery.

### Geospatial
The existing owner-controlled geospatial gateway remains integrated with Earth observation, maps, historical layers and lawful device positioning. Location is DENY by default and requires explicit owner consent.

### Voice and device continuity
Voice is one interface. The same owner authority must work through Web, Android, macOS, text, biometric/device authentication and secure recovery. Wispr Flow is an input adapter, not an authority layer.

### n8n
n8n remains the workflow automation fabric. Vyomaraj/Jarvis decide and orchestrate; ShriYantra governs; n8n executes approved workflow steps; verification and audit return to the cores.

### Continuous content alignment
Weekly/monthly cleaning, provenance recovery, duplicate detection, taxonomy alignment, product/media alignment, Kuber reconciliation, peer synchronization and DR verification remain active maintenance responsibilities.

## New layers integrated into the legacy architecture

### MCP
Inserted under ShriYantra/Harness as the controlled agent-to-tool/resource/prompt fabric.
It cannot receive owner/root authority.

### A2A
Inserted under ShriYantra/Harness as the controlled agent-to-agent delegation fabric.
All delegated tasks are authenticated/authorized, signed where supported, provenance tracked and results verified.

### Production Agent Runtime
The old agent registry is now materialized through a runtime factory that binds identity, role, capabilities, memory, prompt/context, MCP tools, A2A peers, sandbox, durable execution, observability, evaluation, recovery and cost controls.

### Creative Director / Media
The older universal media architecture becomes an execution layer for image, video, 3D, animation, TTS, audio, editing, captions and presentation. Character/voice/style selection remains policy-governed.

### Collaboration / Global earning
The new Collaboration agent connects the existing content/social/revenue architecture to lawful creator, publisher, music, book, copywriting, brand and AI-agent opportunities.

### Social monetization
Social surfaces are controlled publication/analytics adapters. A platform is ENABLED only after actual account authorization, integration tests and runtime evidence.

## Non-negotiable architecture rule
No new technology may replace:
OWNER AUTHORITY → SHRIYANTRA GOVERNANCE → PEER CORES → HARNESS/POLICY → EXECUTION → VERIFICATION → AUDIT → RECOVERY.

MCP, A2A, Arena, n8n, providers, media tools, social platforms and external collaborators are execution dependencies beneath that control model.

## Verification labels
VERIFIED = runtime evidence.
IMPLEMENTED / NOT VERIFIED = code/config exists but runtime evidence is absent.
CONFIGURED / NOT CONNECTED = configuration exists but external account/credential/endpoint is not connected.
BLOCKED = prerequisite prevents safe execution.
NOT APPLICABLE = intentionally not enabled.

Never convert documentation into a false deployment claim.
